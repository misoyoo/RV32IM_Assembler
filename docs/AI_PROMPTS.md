# AI 사용 및 프롬프트 기록

## 1. AI 사용 여부

본 프로젝트는 어셈블러 설계, 구현, 디버깅 및 검증 과정에서 생성형 AI를 사용하였다.

AI는 코드 작성과 수정, 알고리즘 설명, 오류 원인 분석, 테스트 방법 제안 등에 활용했다.

AI가 생성한 코드를 그대로 최종 결과로 간주하지 않았으며, 사용자가 직접 프로젝트에 반영한 뒤 macOS 환경에서 컴파일 및 실행하고 CPUlator에서 동작을 검증했다.

## 2. 초기 생성 프롬프트

초기 구현 단계에서 사용한 주요 요청은 다음과 같다.

> C 언어로 RISC-V RV32IM 어셈블러를 구현하려고 한다. 전체 구조를 설계하고 Parser, Register, Encoder, Symbol Table, Pass 1, Pass 2를 모듈별로 나누어 구현 방향을 제안해줘. R/I/S/B/U/J 명령어 형식과 CSR 및 System 명령어 인코딩을 지원하도록 해줘.

> 어셈블리 소스의 라벨, mnemonic, operand를 파싱하고 `.text`, `.data`, `.bss`, `.equ`, `.global` 및 데이터 지시어를 처리하는 2-pass 구조를 만들어줘. Pass 1에서는 섹션 크기와 심볼 주소를 계산하고 Pass 2에서는 기계어와 초기화 데이터를 생성하도록 해줘.

> 기존 프로젝트의 파일 구조와 함수 인터페이스를 최대한 유지하면서 기능을 단계별로 구현해줘. 정상 동작하는 기존 코드를 불필요하게 전면 교체하지 말고, 수정할 위치와 이유를 구체적으로 설명해줘.

## 3. 기능별 구현 프롬프트

### 3.1 Parser 및 Register

> 어셈블리 소스에서 라벨, mnemonic, operand를 분리하는 Parser를 구현해줘. 빈 줄, 주석, 라벨만 있는 줄, 메모리 operand 및 문자열 내부 쉼표를 고려해줘.

> RISC-V ABI 레지스터 이름과 x0~x31을 내부 레지스터 번호로 변환하는 함수를 구현해줘. fp와 s0 별칭도 고려해줘.

### 3.2 Encoder

> R/I/S/B/U/J 형식의 RV32IM 명령어 인코더를 구현해줘. 각 형식의 bit field를 올바르게 배치하고 immediate 범위와 레지스터 번호를 검사하도록 해줘.

> CSR 및 System 명령어 인코더를 별도로 구현하고, 각 명령어의 인코딩 결과를 확인할 수 있는 테스트를 제안해줘.

### 3.3 Symbol Table 및 Directives

> 심볼 테이블을 동적 배열로 구현하고 주소, 유형, 전역 여부 및 정의 여부를 관리하도록 해줘. `.global`과 `.globl` 선언 후 실제 라벨 정의가 연결되도록 해줘.

> `.byte`, `.half`, `.word`, `.ascii`, `.asciz`, `.space`, `.align`, `.equ`를 처리해줘. 표현식 평가와 문자열 escape 처리도 고려해줘.

### 3.4 Pass 1 및 Pass 2

> Pass 1에서 섹션 크기와 메모리 주소를 계산하고 라벨을 심볼 테이블에 등록하도록 구현해줘. 기본 Text Base는 0x00010000으로 설정해줘.

> Pass 2에서 기계어와 데이터를 생성하고 Raw Binary 및 Listing 파일을 출력하도록 구현해줘. 바이너리 크기와 예상 크기를 비교하는 검증도 추가해줘.

## 4. 검증 프롬프트

### 4.1 제공 예제 검증

> 제공된 어셈블리 예제를 수정하지 않고 Pass 1과 Pass 2에서 정상 처리되는지 확인할 수 있도록 테스트 명령을 작성해줘. 각 예제의 `.bin`과 `.lst` 출력도 확인해줘.

> 예제 1~4의 Text Base가 모두 0x00010000인지 확인하고, Listing의 첫 명령어 주소도 확인할 수 있는 터미널 명령을 제안해줘.

### 4.2 오류 검증

> 존재하지 않는 mnemonic, 중복 라벨, 정의되지 않은 심볼, 잘못된 레지스터, immediate 범위 초과 및 BSS에서 허용되지 않는 지시어를 테스트해줘. 각각 Pass 1과 Pass 2 중 어느 단계에서 실패하는지 확인하고, 실패 후 잘못된 출력 파일이 생성되지 않는지도 검사해줘.

### 4.3 CPUlator 검증

> 생성한 Raw Binary를 CPUlator RISC-V DE10-Lite에 로드하고 실행하는 절차를 설명해줘. 메모리 시작 주소와 PC 설정을 구분하고, 0x00010000에서 실행되는지 검증하는 방법을 알려줘.

> 각 예제의 요구 기능과 실제 시뮬레이터 동작을 비교해줘. 영상만으로 확인할 수 있는 동작과 소스 코드를 확인해야 하는 내부 구현을 구분해줘.

## 5. 디버깅 프롬프트

> 현재 소스 코드와 실제 컴파일 및 실행 로그를 기준으로 오류 원인을 찾아줘. 추측으로 코드를 수정하지 말고 실제 함수와 코드 위치를 확인해줘.

> 정상 동작하던 기존 코드를 불필요하게 전면 교체하지 말고 필요한 부분만 수정하도록 안내해줘.

> 오류가 발생한 부분의 원인, 수정한 내용을 함께 설명해줘.

> C 코드의 들여쓰기는 4칸을 사용하고, 수정할 위치를 정확하게 알려줘.

## 6. 실제 검증 및 사용자 수행 과정

AI가 제안한 코드 및 테스트 절차는 다음 과정을 통해 확인했다.

1. 제안된 코드를 프로젝트에 반영한다.
2. macOS 터미널에서 직접 컴파일한다.
3. 정상 예제 9개를 어셈블하고 Binary Validation 결과를 확인한다.
4. 오류 입력을 별도로 만들어 Pass 1 및 Pass 2의 실패 여부를 확인한다.
5. Listing과 Symbol Table의 주소 및 유형을 확인한다.
6. CPUlator에서 Raw Binary를 로드하고 PC를 0x00010000으로 설정해 실행한다.
7. 예제별 주변장치 입력과 출력 결과를 확인하고 동작 영상을 기록한다.

## 7. 프롬프트 기록에 관한 설명

본 문서의 프롬프트는 프로젝트 진행 과정에서 사용한 요청을 주제별로 정리한 것이다. 대화 전체의 모든 요청을 글자 단위로 복원한 축어록은 아니며, 초기 생성, 기능 구현, 검증 및 디버깅에 사용한 대표 요청을 요약·재구성한 기록이다.

## 8. AI와 사용자 역할 구분

| 구분 | 수행 내용 |
|---|---|
| AI | 설계 제안, 코드 작성·수정 지원, 개념 설명, 디버깅 방향 제시, 테스트 절차 제안 |
| 사용자 | 코드 반영, 로컬 빌드, 직접 실행, 검증용 입력 수행, CPUlator 시뮬레이션, 실행 결과 확인 및 영상 촬영 |

AI를 사용한 사실을 명시하며, 프로젝트의 최종 검증 결과는 실제 컴파일 로그, Binary 및 Listing 출력, 소스 코드와 CPUlator 실행 결과를 바탕으로 기록하였다.
